# GSTR-2B Reco — setup and operating guide

**Sidebar → GSTR-2B Reco** (under GST Dashboard). It compares what is **booked in Zoho Books** with what suppliers have **reported to the GST portal (GSTR-2B)**, separately for each of your GST registrations, and tells you what matches, what is missing on either side, and what differs.

*Written for the finance team. How it is built, the verified Zoho / GST facts and the rules are in `DESIGN.md` in this folder.*

## What it does — and does not do

| It does | It does not |
|---|---|
| Reads bills, vendor credits and GST-bearing expenses from Zoho Books — **read-only** | Change anything in Zoho: it cannot create bills, post journals, file returns or send messages |
| Imports the GSTR-2B file you download from the GST portal (JSON or Excel), keeps the original untouched, tracks versions | Connect to the GST portal by itself (that needs a GSP subscription and OTP — Phase 3) |
| Matches by clear written rules and shows **why** every row got its status | Decide whether tax credit is **eligible** — "matched" is not "eligible". The ITC register is **Phase 2** and is not built yet |
| Shows Books-only GST as **unresolved exposure** (with the Section 16(4) deadline), never as "lost" | Match across different GSTINs or companies, or on a vendor name / similar amount alone |

## One-time setup (CFO / administrator)

1. **Restart the dashboard server once** (the module's server code is new) and press **F5** in the browser. The sidebar then shows **GSTR-2B Reco** to administrators.
2. **Give people access:** *User Settings → GSTR-2B Reco*. Tick the module, then the rights each person needs — they are ticked one by one and never by "All":
   * **Prepare** — Zoho sync, upload statements, run reconciliation, owner / notes · **Review** — link, approve suggestions, exclude documents, mark Accepted / Resolved · **Approve / lock** — Phase 2 · **Configure** — companies, GSTINs, tolerances, schedule.
   * Typical roles: *preparer* = Prepare · *reviewer* = Prepare + Review · *CFO* = all four · *read-only* = module ticked, nothing else.
   * An administrator can also limit a person to particular companies or GSTINs (*Settings & audit → Access*).
3. **Connect a company** — *Settings & audit → Companies & GSTINs → Add a company*:
   1. **Find the organisations** this Zoho login can read (or type the organisation id). Pick the company.
   2. **Read its branches and GSTINs.** Each Zoho branch carries a GSTIN; the screen groups branches by GSTIN and checks each one (correct check digit, branch addresses in the right state, same PAN). Branches **without a GSTIN** are listed — their documents cannot be reconciled until a GSTIN is entered in Zoho.
   3. Tick the GSTINs that are yours, name the company, confirm the **supplier invoice date field** (DevX uses `cf_vendor_bill_date`; for another company check which custom field holds the supplier's invoice date) and **Save**. The server re-checks every GSTIN against Zoho before it is saved.
   Nothing is pre-filled — organisation ids, GSTINs and branch mappings are never assumed.
4. **(Recommended) a read-only Zoho token.** The module only reads either way. For least privilege create a separate Zoho token with read scopes only (`ZohoBooks.bills.READ`, `.vendorcredits.READ`, `.expenses.READ`, `.contacts.READ`, `.settings.READ`, `.vendorpayments.READ`) and put it in `.env` as `GSTR2B_ZOHO_REFRESH_TOKEN` (plus `GSTR2B_ZOHO_CLIENT_ID` / `GSTR2B_ZOHO_CLIENT_SECRET` if the Zoho client differs from the dashboard's). The top-right of the screen says which credentials are in use. *Settings → Check Zoho access* tests each area.
5. **Record GSTR-9 filing dates** (*Companies & GSTINs*, per GSTIN and year) once the annual return is filed — it can close the ITC claim window before 30 November.

## First sync

*Imports & sync → Start the first sync…* Until it has been started the card says **First sync — Not started**, shows a "Step 1" box, and **Sync changes now** is greyed out (that button only picks up changes made after a first sync). Choose the months and click **Start syncing this period**.

* **How long.** Zoho's list has no GST amounts, so every document that can be matched needs **one call of its own**. The sync makes about **90 calls a minute** (changeable), so a month of DevX — about 600 documents — takes about 7 minutes, and April–November 2026 — about 4,900 — under an hour.
* **Nobody has to watch it.** Once it has started you can leave the page. Online, the scheduler carries on with the same work at its next call, the page carries on while the module is open, and the GitHub job that follows every push keeps going until it is done; on the office PC the server runs it through. If it is interrupted — a time limit, a daily limit, a closed browser, a restart — it continues from where it stopped: no month is listed twice and no document is read twice.
* **What "complete" means.** The card shows the documents **found in Zoho** (that can be matched), **fully fetched** (with amounts and tax), **pending** and **failed**, with a percentage. The first sync is *Completed* only when every month has been listed **and** every document that can be matched has its amounts. A document Zoho would not hand over after three attempts is counted as *failed*, listed on the card with Zoho's answer, tried again once every night and by **Try these again** — the status then reads *Completed — some documents could not be read*, never plain *Completed*.
* **What a sync spends calls on.** Amounts are read only for GSTINs that are **switched on** (*Settings → Companies & GSTINs → Active*) — a GSTIN switched on later is read at the next sync — and only for documents dated **from the first month synced** (old vendor credits, which Zoho lists back to the beginning, wait until a period that reaches them is synced). The card lists everything kept out of matching, with the reason.
* **Going further back.** *Sync a period…* with earlier months, a few at a time; last year's invoices first — their ITC window closes first (see the deadline notice on Overview).

After the first sync, changes are picked up automatically: on the office PC at **1:20, 3:20, 6:20 and 9:20 PM** (changeable), online every 15 minutes (next section). **Sync changes now** does the same on demand, and **Check against Zoho now** re-lists every synced month (deleted documents, totals, failed documents). Two syncs of the same company never run at once — the second is told one is already running.
## Automatic sync online

Online (Vercel) the dashboard is called by **Vercel's own scheduler** (`vercel.json`), round the clock:

* **Every 15 minutes** (at :07, :22, :37 and :52 past each hour): it asks Zoho for the bills, vendor credits and GST expenses that were **added or edited since the last check** — whatever their invoice dates, so an older bill edited today is included — and fetches the amounts of those and of anything still pending. The checkpoint moves only after everything Zoho listed has been saved, and each check re-reads the 15 minutes before it, so nothing falls between two checks; a document is stored once, under its Zoho id. The history is not listed again and nothing is downloaded unless Zoho says it changed. A check that finds nothing costs 4 Zoho calls and about a second, and is not written to *Recent sync runs* or the audit trail.
* **1:00 AM India time:** a full comparison with Zoho — every synced month is listed again, documents **deleted** in Zoho are removed (a deletion never shows up as a change), every stored total is compared with the total Zoho lists, and failed documents are tried again. The result is on the card ("Checked against Zoho Books on …"). The same check runs once right after a first sync completes.
* **Needs the Vercel Pro plan.** On the free (Hobby) plan Vercel refuses a schedule that runs more than once a day, and the deployment fails. If the plan is Hobby, remove the two `gstr2b` lines from `vercel.json` (the sync then runs whenever the module is open, after every push, and when someone presses a button).
* **Seeing that it works.** The card shows the scheduler as it is **observed**: *Automatic sync — last call 13 Nov, 12:22 am · nothing new · next due about 12:37 am*. Before the first call it says *not seen yet*; if calls stop for more than half an hour it says so in red. In Vercel: the project → *Settings → Cron Jobs* lists the two schedules and their last runs.
* **While the module is open** it also keeps itself fresh: when it is opened, and every few minutes after, it runs a step if something is due (the rest of a sync, documents waiting, or no check in the last 10 minutes). So even with every scheduler down, the data is brought up to date as soon as someone opens the module.
* **The GitHub job** (`.github/workflows/gstr2b-sync.yml`, using the repository secrets `APP_URL` and `CRON_SECRET` that the dashboard's other jobs already use) is not the timer any more — GitHub's schedule turned out not to fire on this repository (not one run in 4.5 hours on 12 Nov 2026). It starts after every **push** (once Vercel reports the new version as live) and on **Run workflow**, and keeps asking for the next step while there is more to do: that is what carries a first sync of thousands of documents through without a page open. If Vercel could **not** put the pushed version online, the job fails and says so — a red mark in GitHub → Actions, and GitHub's usual e-mail — instead of syncing with the old version. A wrong `CRON_SECRET` makes it fail with a clear message.
* **Limits** (*Settings → Schedule & sync limits*): calls per minute (90), calls at the same time (4), calls per day for this module (30,000), and calls kept free for the other integrations (15,000). Zoho counts every integration of the organisation against **one daily allowance — 90,000 calls on the current plan, starting again at midnight India time** — and allows one user 150 calls a minute and 20 at once (read from Zoho's own answers on 12 Nov 2026). The sync reads Zoho's count after every call and stops for the day when the organisation's remaining allowance falls to the number kept free, so a long sync cannot starve the other integrations. If Zoho answers "too many requests", it waits as long as Zoho asks and carries on. Nothing is written to Zoho.
* **Faster than 15 minutes** would need a Zoho webhook (a rule created in Zoho Books that notifies the dashboard); it is not built, and a monthly GSTR-2B reconciliation does not need it.
## Every month (suggested routine)

1. **After the 14th** (when GSTR-2B is generated) — and again after any IMS action and *recompute* — download GSTR-2B for **each GSTIN** from the portal (Returns → GSTR-2B → Download; JSON is preferred).
2. **Imports & sync → Upload** the file → **Preview**. Check: the GSTIN and period read from the file, the sections and totals, any row problems, the "portal summary check" (Agrees / Differs). Then **Import**. A second upload for the same GSTIN and month becomes the next **version**; an older file never replaces a newer one; the same file cannot be imported twice.
3. **Work the queues** (each is a filtered view of the same workbench):
   * **Mismatch & duplicate review** — amounts that differ, suggested matches, duplicates, GSTIN problems.
   * **Books only** — in Zoho, not reported by the supplier: chase the supplier. The row shows the ITC claim deadline.
   * **GSTR-2B only** — reported by a supplier but not in your books.
   Click a row for the full explanation, both source documents, and what to do. Set an **owner**, **workflow** and **next action** so nothing is lost. *Suggested* matches must be **approved** with a reason; they are never accepted automatically.
4. **Overview** before you file GSTR-3B: *Pending review*, *Potential credit exposure*, and the deadline notice. **Export to Excel** for the working papers (it includes the bridge that ties Books to GSTR-2B per tax component).

## How to read a row

**Status (one per row):** *Exact matched* · *Matched within approved tolerance* (each tax component within its own rounding tolerance, default ₹1) · *Suggested match — review required* · *Mismatched* (same document, an amount differs beyond tolerance) · *Books only* · *GSTR-2B only* · *Excluded* (kept out of matching, always with the reason).

**Flags (extra notes on a row, never added up):** duplicate suspected · invalid GSTIN · wrong supplier / recipient GSTIN · cross-period / late reporting / across financial years · amendment · credit / debit note · reverse charge · incomplete or unsupported data · ITC not available per the portal · invoice date assumed · ambiguous · number-normalisation collision.

**Rules, in short:** same supplier GSTIN + document type + number + date → matched (R1); number equal after ignoring case, spaces and punctuation → matched (R2); leading zeros, small typos, nearby dates, split or consolidated invoices, another GSTIN of the same PAN → only ever **suggested**. Different recipient GSTINs and companies are never mixed.

## Please confirm (assumptions the module makes)

| # | Assumption | Where to change |
|---|---|---|
| 1 | In Zoho, **Credit Note #** is the supplier's credit-note number (otherwise use Reference #) | Companies → credit-note number |
| 2 | A **debit note received from a supplier** is booked as a bill | — (needs a convention) |
| 3 | The supplier's invoice date is in the custom field set per company; if empty the **posting date** is used and flagged "assumed" — such rows are never auto-matched on number alone | Companies → invoice date field |
| 4 | **Expenses with GST** (21 of 2,400 this year) are included but their date is never trusted as an invoice date | — |
| 5 | Reverse-charge purchases: the module splits the RCM tax into IGST / CGST / SGST by place of supply (Zoho keeps it on the lines) and flags it | — |

## Known limitations

* **GSTR-2B files:** the **Excel layout was checked on 12 Nov 2026 against a real portal workbook** (GSTR-2B of September 2026, one GSTIN): the B2B sheet is read in full (69 invoices, tax totals equal to the portal's own summary sheet, dates and period read correctly). That workbook had no rows in the other sheets, so credit / debit notes, amendments, e-commerce, ISD and import sheets are verified only against **invented rows under the portal's real headings** (`tests/portal_excel.test.js`) — **please upload a month that has credit notes and amendments** to confirm them on real data. The **JSON layout** is still taken from third-party documentation of the GSTN API (GSTN publishes no public schema) and has not been run against a real portal file — please upload one real JSON too (Preview does not import anything). The importer reads by heading text, shows exactly what it read, and refuses to half-import a sheet. Sheets without a single document raise no notice; the IMS "(Rejected)" sheets and the "(ITC Reversal)" sheets are not imported (the preview lists them when they hold rows). A GSTIN with genuinely **no** inward supplies in a month cannot be imported yet ("No documents were read from this file" blocks it).
* **Sections imported but not matched yet** (shown as *Excluded* with the reason): ISD, imports of goods / SEZ, e-commerce operator documents, Rule 37A reversals.
* **Phase 2 is not built:** ITC register (eligibility, claim / reversal / reclaim), 180-day review with partial payments, GSTR-3B working, approvals, vendor message **drafts**, period locks and snapshots, evidence attachments. **Phase 3:** direct GSTN / IMS (needs a GSP subscription), supplier filing-status lookup. The screens say so; the Excel has labelled placeholder sheets.
* **PC and Vercel keep separate copies** of this module's data (statements, decisions, notes and the synced Books). Choose one as the place where finance works. The office PC syncs by itself 4 times a day and accepts files up to 40 MB; online the sync runs every 15 minutes on Vercel's scheduler (Pro plan) and uploads are limited to 4 MB. Online, the module's data sits in Neon and the original statements in private Blob. The Neon side is tested with the dashboard's real database code (only the connection is simulated); the Blob side uses the dashboard's shared file store, tested with an in-memory stand-in. **Vercel's scheduler itself cannot be tested before it is deployed** — after the update goes online, check that the card shows "last call … by Vercel's scheduler" within 15 minutes.
* Journals and opening ITC balances are not read; bills of unregistered / overseas suppliers are listed but cannot appear in GSTR-2B.
* The Section 16(4) deadline uses the invoice's financial year and the GSTR-9 date you record. It is a reading of the statute, **not legal advice** — confirm with your tax advisor.

## If something looks wrong

| You see | Meaning / what to do |
|---|---|
| "N Books documents are still waiting for their amounts" | A sync is not finished yet. Imports & sync shows the progress and the estimate; it carries on by itself. Figures are incomplete until it is done. |
| "GSTIN … is not set up" when uploading | Add that GSTIN under Companies & GSTINs first. |
| A row says "Changed in Zoho — not refreshed" | The bill was edited after it was read; the next sync refreshes it, or use **Refresh from Zoho** in the row. |
| "Possible wrong recipient GSTIN" | The same invoice is Books-only under one GSTIN and GSTR-2B-only under another. Nothing is matched across GSTINs — decide which registration the invoice belongs to. |
| Bridge shows "DOES NOT TIE" | Should never happen; stop and report it (it means a document was lost or counted twice). |
| Sync paused: "daily budget" / "Zoho limit" | It resumes after midnight India time. Raise this module's daily number, or lower the number kept free for other integrations, in Schedule & sync limits — the organisation's allowance is shared. |
| "Automatic sync — not seen yet" long after an update, or the red "stopped calling in" | Vercel's scheduler is not calling: check Vercel → the project → Settings → Cron Jobs (and that the team is on the Pro plan). Meanwhile the module still syncs whenever it is open, and "Sync changes now" works. |
| First sync "Completed — some documents could not be read" | The documents are listed on the card with Zoho's answer. Open one in Zoho to see what is wrong with it; **Try these again** reads them at the next sync, and they are retried every night. |
| "Checked against Zoho" shows a difference | A stored total is not what Zoho lists now (an edit that did not move Zoho's "last modified"). The documents are re-read at the next sync; if it stays, report it. |

## Tests and what was verified

* `npm run test:gstr2b` — **144 tests, all passing**: matching (24), GSTR-2B import (8), GSTR-2B Excel in the portal's real layout (6), Zoho → document conversion (15), sync (38), automatic sync (19, including the GitHub job's own script run against a local stand-in for the dashboard and for GitHub; those three need `bash` and are skipped without it), reconciliation end to end (12), dashboards (9), HTTP API (8), online mode (4), and one that runs the online build's code checker over the module's screens (the office PC builds with that checker switched off, Vercel does not — on 13 Nov 2026 a comment it rejects built here and failed the deployment). The fake Zoho **refuses what the real one refused** (for example `sort_column=last_modified_time` on expenses) and can **page badly the way the real one did** (a document missing from a list, another returned twice) — it once accepted anything, and a request that real Zoho rejects passed every test. They use **synthetic** data and a fake Zoho shaped exactly like the responses seen live. The online-mode tests run the whole flow (sync in steps, the keep-fresh call, upload, review, export, demo) on the dashboard's **real** `server/db.js` with only the Neon connection simulated in memory, Blob simulated in memory and a read-only disk; they check that every screen loads on a brand-new database, that nothing is written to the disk, that every key sits under the module's own `g2b_` prefix, and that a momentary database read failure stops the request instead of overwriting a stored record. (An earlier version simulated `db.js` itself, which hid a bug that showed online on first use — a record that does not exist yet came back as `null`.)
* **Browser test** (headless Chrome against an isolated server with a fake Zoho; no real data touched): **35 of 35 checks passed** with no console errors — sidebar entry, onboarding wizard, first sync, upload / preview / import, repeated-upload refusal, every tab, the drawer, settings, audit-chain check, demo data, Excel download. The reworked sync card was rehearsed the same way **in online mode** (13 Nov 2026, **24 of 24**): a first sync running in steps with the percentage climbing, a document Zoho refuses (reported as failed, never as complete), the scheduler's calls appearing on the card, the check against Zoho, a new and an edited bill picked up by a scheduler call, "Try these again", the module refreshing itself when opened, the red notice when the scheduler stops calling, and the new limit settings.
* **Live, read-only against your Zoho (11 and 12 Nov 2026):** field shapes, branch GSTINs, change filter, organisation list, and data-quality measurements on the real bills — recorded in `DESIGN.md` §4 and §6. On 12 Nov the change feed was also run end to end against the real DevX organisation (read-only, a throw-away store, 21 calls): bills, vendor credits and expenses all answered, 23 recently changed bills were listed and their amounts fetched. Nothing was written to Zoho.
* **Live rehearsal of the reworked sync (13 Nov 2026, read-only, a throw-away folder on the office PC, the real DevX organisation, April–November 2026, all 8 GSTINs):** starting from a store in the state the online one was in (7,650 documents listed by the previous version, 225 with amounts), the scheduler's steps read the **4,643 waiting amounts in 19 steps = 53 minutes** (88 documents a minute at the default 90 calls a minute; Zoho's per-minute allowance never fell below 142 of 150; one answer from Zoho failed and was retried by itself; no document failed). The first sync then showed **Completed: 4,862 of 4,862**. Checked against Zoho: **bills — Zoho's own count 7,100, read 7,100, stored 7,100; 2,346 kept out of matching (no supplier GSTIN, void, not INR); all 4,754 with amounts have exactly the total Zoho lists (₹133,17,99,152.24 after TDS; taxable value ₹118,02,27,194.41, GST ₹20,89,41,901.34)**; vendor credits — 522 counted and read, 77 dated from April with amounts, all agreeing (₹1,42,75,535.00); expenses — 3,216, of which the 31 that carry GST are kept and agree. One reconciliation over all 8 GSTINs took half a second on the PC. A scheduler call with nothing new: 4 Zoho calls, under 2 seconds, not recorded. **Changes:** the store was rolled back to the previous morning (39 documents removed, 64 given their old "last modified") and one change check brought back all 39 new documents and refreshed all 64 edited ones — 45 of them dated in earlier months, the oldest in April 2025 — with 3 list calls and 92 amounts calls in 63 seconds, without listing the history. **Found on the way:** Zoho's vendor-credit list, sorted by date, returned 522 rows but only 519 different documents; the listing now sorts by created time and checks itself against Zoho's own count (`DESIGN.md` §4.1). **Not covered by this rehearsal:** the online database and Vercel's scheduler — they can only be seen working after the update is deployed.
* **Scenarios covered:** exact and rounded matches · invoice-number collisions · wrong GSTIN · identical totals with different tax components · duplicates and repeated uploads · split and consolidated invoices · late reporting across financial years · credit notes · amendments · recomputed statements · edited, voided and deleted Zoho records · interrupted sync and safe retry · only-affected-partitions reprocessing · reviewer decisions surviving re-runs · access limits · audit tamper detection.
* **Not yet testable (Phase 2):** partial payments (180-day), duplicate-claim prevention, locked-period changes.

## Demo data

*Settings & audit → Demo data* (administrators) creates **Demo Company (synthetic)** with made-up suppliers, bills and statements that show every situation above, including invoices close to the FY 2025-26 deadline. It never touches Zoho, is labelled **DEMO** on every screen and in every export, and **Remove** deletes it completely. Real companies are unaffected.
